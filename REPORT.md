# EXPERIMENT NO: 13

**AIM:** Mini-Project: CampusRSVP, an Event RSVP Web Application for College Students (All COs).

## PROBLEM STATEMENT
Student clubs usually manage event sign-ups through scattered WhatsApp groups and Google Forms, which makes it hard to discover events, enforce capacity limits or track who is attending. The aim is to design and build a Python-based web application where students can browse campus events and RSVP in a few clicks, and organizers can create events and monitor attendance.

## SOFTWARE/IDE USED
Google Colab / Jupyter Notebook (`run_in_colab.ipynb` installs and launches the app), Python 3, Flask, Flask-SQLAlchemy with SQLite, HTML/CSS/JavaScript, pytest, Antigravity IDE.

## IMPLEMENTATION
### 1. Purpose of developing the application using Flask
Flask is a lightweight Python web framework. It was chosen because it gives clear control over routing, request handling, templating (Jinja2) and sessions without heavy boilerplate, so each concept (URL routing, forms, ORM, authentication, REST endpoints) is visible in the code. The application follows the MVC idea: SQLAlchemy models (`Event`, `RSVP`), Flask routes as controllers and Jinja2 templates as views. It solves a real campus problem by replacing messy forms and chat groups with one searchable, capacity-aware RSVP system.

### 2. Frontend screenshots
**Figure 1: Home page (light mode)**

![Home page (light mode)](screenshots/01_home_light.png)

The landing page shows the hero search bar, a stats strip (total events, total RSVPs, most popular event), category chips and a responsive grid of event cards. Each card has a colour-coded category, date, venue and a progress bar showing how full the event is. Data comes from the `Event` table through the `home()` route and is rendered with a Jinja2 template.

**Figure 2: Home page (dark mode)**

![Home page (dark mode)](screenshots/02_home_dark.png)

The theme toggle in the navbar switches CSS variables and stores the choice in `localStorage`, so the preference is remembered across pages.

**Figure 3: Category filter**

![Category filter](screenshots/03_home_filtered_tech.png)

Clicking the 'Tech' chip sends `?category=Tech` to the same route, where SQLAlchemy filters events with `filter_by(category=...)`. The search box works the same way using `ilike` on title, venue and description.

**Figure 4: Event detail page**

![Event detail page](screenshots/04_event_detail.png)

Shows the full description, a live JavaScript countdown, avatars of confirmed attendees and the sticky RSVP panel with remaining seats. An 'Add to calendar' button downloads an `.ics` file generated by the backend.

**Figure 5: Client-side validation**

![Client-side validation](screenshots/05_rsvp_validation_error.png)

Invalid input (too-short name, malformed email) is stopped by JavaScript before submission and reported as a toast. The server repeats every check, so validation cannot be bypassed.

**Figure 6: Successful RSVP**

![Successful RSVP](screenshots/06_rsvp_success.png)

After a valid POST the server stores a row in the `rsvp` table, flashes a success message and redirects (Post/Redirect/Get). The seat count and attendee list update immediately.

**Figure 7: Capacity handling**

![Capacity handling](screenshots/07_event_almost_full.png)

Only 'Going' RSVPs use a seat. When an event reaches capacity the 'Going' option is disabled and the page shows a 'Full' state, while 'Maybe' is still allowed. Cards on the home page show an 'Only N left' badge when seats are low.

**Figure 8: My RSVPs**

![My RSVPs](screenshots/08_my_rsvps.png)

A student enters their email to see every event they responded to. The dropdown lets them change between Going/Maybe or cancel; each change is a POST to `update_rsvp()` that rechecks capacity.

**Figure 9: Organizer login**

![Organizer login](screenshots/09_admin_login.png)

The organizer area is protected by a password (environment variable `ADMIN_PASSWORD`) and Flask session cookies. Unauthenticated visits to `/admin` are redirected here by the `admin_required` decorator.

**Figure 10: Organizer dashboard**

![Organizer dashboard](screenshots/10_admin_dashboard.png)

Organizers can create events with a form (validated server-side), see all events with going/total counts, and delete events (cascade deletes their RSVPs).

**Figure 11: Attendee list and CSV export**

![Attendee list and CSV export](screenshots/11_admin_attendees.png)

Lists every RSVP for an event with name, email, status and time. The 'Export CSV' button streams the list as a downloadable file using Python's `csv` module.

**Figure 12: Custom 404 page**

![Custom 404 page](screenshots/12_404_page.png)

A Flask error handler returns a friendly page for unknown URLs instead of the default browser error.

**Figure 13: Responsive layout (mobile)**

![Responsive layout (mobile)](screenshots/13_home_mobile.png)

CSS grid and media queries reflow the layout to a single column on a 390px-wide phone screen.

### 3. Backend screenshots
**Figure 14: Flask development server log**

![Flask development server log](screenshots/B1_server_log.png)

Terminal output of `python app.py`. Each line is one HTTP request handled by Flask, e.g. `GET /event/1 200`, `POST /event/1 302` (RSVP saved, then redirect), `GET /admin 302` (not logged in, redirected) and `GET /nothing-here 404`.

**Figure 15: Automated tests**

![Automated tests](screenshots/B2_pytest.png)

`pytest` runs six tests against a temporary database: RSVP creation, duplicate blocking, capacity enforcement, email validation, admin authentication and the 404 page. All pass.

**Figure 16: Project structure**

![Project structure](screenshots/B3_project_structure.png)

Flask application factory in `app.py`, SQLAlchemy models, Jinja2 templates, static assets, seed script and tests, kept separate for readability.

**Figure 17: REST/JSON endpoint**

![REST/JSON endpoint](screenshots/B4_api_events_json.png)

`GET /api/events` returns events as JSON including live `going` and `spots_left` values. It demonstrates how the same data layer can serve other clients such as a mobile app.

**Figure 18: SQLite database**

![SQLite database](screenshots/B5_database_tables.png)

Contents and schema of `event` and `rsvp` tables. A foreign key links each RSVP to an event, and a unique constraint on (event_id, email) guarantees one RSVP per student per event at the database level.

## CONCLUSION
This experiment showed how a complete database-backed web application can be built in Python using Flask: routing, Jinja2 templates, SQLAlchemy ORM models, form handling and validation on both client and server. Enforcing rules such as one RSVP per email and event capacity taught us to put integrity checks in the database and backend, not only in the UI. Writing automated tests, a JSON API and a seed script made the project reliable and easy to demo. Overall the project strengthened our full-stack skills across all course outcomes.
